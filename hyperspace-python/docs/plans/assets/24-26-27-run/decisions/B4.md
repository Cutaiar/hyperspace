## The `[[devices]]` blocks the owner writes

An OSC phone app (TouchOSC, Lemur, GyrOSC, an Open Stage Control page, a Max/Pd patch — anything
that sends OSC over UDP). Point the app at the Mac's LAN address, port 9000:

```toml
[[devices]]
role = "phone"            # the scheme: its sources are phone:x, phone:y, phone:hit
kind = "osc"
port = 9000               # UDP; host = "0.0.0.0" (every interface) is the default
axes = ["/x", "/y"]       # the app's fader / XY addresses → phone:x, phone:y (continuous)
hits = ["/hit"]           # the app's button addresses → phone:hit (a trigger with velocity)
# rest = 0.5              # where the axes idle (default 0), or per address: rest = { "/y" = 0.5 }
# range = [-1.0, 1.0]     # what the app sends (default [0, 1]); mapped onto 0–1 and clamped
# timeout = 5.0           # seconds of silence before the line reads `lost`
# hold = true             # while lost the axes keep their last values; false lets the routes go
```

A multi-level address keeps its path: `axes = ["/1/fader1"]` is `phone:1/fader1`.

The recorded cloud (the fixture copied into the home, or any `write_clouds` file):

```toml
[[devices]]
role = "scan"             # published as cloud:scan
kind = "cloud"
file = "clouds/knot.npz"  # relative to the home (the folder config.toml is in)
# rate = 12               # frames per second (default: the file's own)
# loop = true             # false holds the last frame
```

## 1. Register-row drafts (`docs/DECISION-REGISTER.md` format; the docs WP numbers them)

### 1xx. An OSC device's role is its scheme; an address is a source name; its hits are rows under the same scheme

- **Built.** `[[devices]] kind = "osc"` with `role = "phone"` feeds the scheme `phone` (B1's
  "the role is the scheme" for a new device — the prompt's `osc:<role>.<name>` predates it):
  `axes = ["/x", "/y"]` are the lanes `phone:x`, `phone:y` — the address without its leading
  `/`, a deeper path kept (`/1/fader3` → `phone:1/fader3`) — published with their names, labels
  (the name) and rests, so a route names them like `hand:right.roll`, and the ROUTING page and
  `Learn phone` offer them. `hits = ["/hit"]` are triggers under the **same** scheme
  (`phone:hit`): rows through the table, like a pad button's. For that, a device says which
  schemes it delivers rows under (`Base.rows`, default `schemes − feeds` as B2 had it; the OSC
  device's role when it has hits), and the kind says what an entry would publish before it is
  made (`Base.publishes(role, entry)`), so `make` refuses an OSC role another device already
  feeds (`role = "axis"` after the pad), and an `off` OSC entry still lists its scheme and its
  hit rows (a preset row on it waits). A role that is a row kind or a built-in scheme (`cc`,
  `key`, `pad`, `lane`, `lfo`, `cloud`) is an error line on open.
- **Other options.** (a) `osc:<role>.<name>` (the prompt's text: one `osc` scheme for every OSC
  device — B1's rule says otherwise, and two phones would share one fed vector). (b) Hits under
  their own scheme (`hit@phone:hit`, after B2's MIDI qualifier) — a Learn armed for `phone`
  could not take a hit, and the page would show a second scheme for one device. (c) Hits as a
  fed 0/1 lane (no velocity, no rows — against decision 13).
- **To reverse.** `OscDevice.publishes` / `rows` and the `rows` read in
  `DeviceRegistry.row_schemes`: an hour; presets name `phone:x` only once the owner writes them.
- **Rough edge.** Because `phone` is both fed and a row scheme, the referee accepts any op on a
  `phone:` row (a hand-written `phone:x` with op `toggle` is kept and never acts). An OSC device
  listed with no `hits` does not take rows: a button row on its scheme is refused when added.
  **A hit row while its device is not listed** (decision 11 holds): in `bindings.json` a
  `phone:hit` toggle row with no phone in the list is kept dormant and written back unchanged
  (`Bindings.load` runs only the referee); a preset drops every non-performer route row whatever
  the devices (as before plan 27: hit rows are the session's, never a preset's). The only
  refusal tied to the device's absence is interactive — `_check` on add / enable / replace:
  re-enabling a disabled `phone:hit fire` row while no phone is listed is refused with "'fire' is
  not an op for a phone source"; listed (even off), it is accepted
  (`tests/test_osc.py::test_a_session_hit_row_waits_while_its_device_is_not_listed`).
- **Judge it.** Checks W.B4.1, W.B4.2.

### 1xx. OSC values: the first number, the entry's range onto 0–1; NaN until heard; held while lost

- **Built.** An axis's value is the message's first number (an int or float; a bool, a string
  or a NaN is skipped) — **only a message's first number is read**: an XY pad's second value is
  unreachable in this proof device — mapped from `range` (default `[0, 1]`, what most phone apps
  send) onto 0–1 and clamped. **`range` is the axes' only**: a hit's velocity is its first
  number clamped to 0–1, never mapped through `range`. An axis no message has reached reads NaN, so its routes stay dormant — a
  `position` row does not jump the param to the rest before the phone moves (decision 24). The
  device is `connected` while any message (a listed address or not) arrived within `timeout`
  (default **5 s**), `lost` before the first and after a silence. While lost the axes **hold**
  their last values (`hold = true`, the default: a phone app sends only on change, so a fader
  left alone must not snap back); `hold = false` feeds None (routes let go) and forgets the
  values, so on return only re-sent axes act. Closing the device (removed from the list,
  changed, quit) takes its scheme off the router — the vector, the labels, the names and the
  rests — so nothing is held and the ROUTING source combo no longer offers it. A `timeout` that
  is not a positive number (`timeout = "5"`) is an error line, as a bad `range` or `rest` is.
- **Other options.** (a) Let routes go when lost, always (a fader the performer left alone
  would snap back to the base five seconds later). (b) A shorter timeout (2 s): the line would
  flicker `lost` between touches. (c) Rest instead of NaN before the first message — a
  `position` route would move its param at launch.
- **To reverse.** `TIMEOUT_S`, `hold`, the NaN fill: minutes.
- **Rough edge.** With `hold = true`, a phone that leaves the network leaves its routes where
  they were (the line says `lost`). An accelerometer app that streams continuously is never
  `lost` while the app runs, whatever the phone is doing.
- **Judge it.** Check W.B4.3.

### 1xx. OSC hits: velocity is the first number; `abs` lands it; a press is a velocity above 0

- **Built.** A hit's velocity is the message's first number clamped to 0–1, 1 when the message
  carries none (TouchOSC's push buttons send 1 on press and 0 on release). Its rows act as a pad
  button's (`routing.act`) when the velocity is above 0 — `fire`, `toggle`, `step`, `set`;
  `abs` lands the velocity itself on the param (a trigger fires above 0); `momentary` holds a
  toggle on while the velocity is above 0 and lets go at 0; `hold` does nothing (an OSC hit has
  no duration to time). A Learn armed for the role takes the next hit with a velocity above 0 as
  a button row (`Learn.learn_pad_button`: a trigger fires, a toggle toggles, a fader steps;
  written to `bindings.json`, the session's, like a pad button's) and holds that frame's rows
  back; else the first axis moved 0.25 from its rest (`LEARN_TRAVEL`) as a route
  (`learn_source`; centred when its rest is strictly between 0 and 1).
- **Other options.** (a) Velocity on 0–127 like MIDI (phone apps send 0–1). (b) Hit rows into
  the preset (a pad button's are the session's; plan 24's desk rules are MIDI's). (c) A `hold`
  row timed from press to release (needs the release message every app sends differently).
- **To reverse.** `osc.fire`: one function.
- **Rough edge.** A velocity above 1 (an app sending 0–127) clamps to 1. `learn_pad_button`'s
  "fader steps" picks +1 for every OSC address (its D-pad rule names `hat:DOWN`/`LEFT` only).
- **Judge it.** Check W.B4.2.

### 1xx. The OSC socket is read in `poll`, non-blocking, no thread; UDP 0.0.0.0:9000 by default

- **Built.** `osc.Server` binds a UDP socket on the entry's `host:port` (default `0.0.0.0`, so
  a phone on the LAN reaches it, and `9000`) and the device's `poll` reads every datagram
  waiting, at most 512 a frame (`MAX_DATAGRAMS`); `pythonosc.osc_packet.OscPacket` parses each
  one (a bundle's messages in timetag order, delivered at once); a datagram that is not OSC is
  counted on the line (`… · 3 not OSC`), never raised. A port another program holds is
  `error: OSError: [Errno 48] UDP 0.0.0.0:9000 — Address already in use` on the line and one
  note, retried on the registry's schedule (2 s ×5, then 10 s): it comes up once the port frees.
  `pythonosc` is imported only in `Server`; `devices.kinds()` imports `hyperspace.osc` (the
  module, not the library) like `hands.device`, so the registry can list an OSC entry's scheme
  even while it is off.
- **Other options.** (a) `pythonosc`'s `ThreadingOSCUDPServer` and a dispatcher (a thread per
  device, a lock, a queue — and the tests would race it). (b) `osc.py` imported only when an
  entry names the kind (a lazy branch in `kind_class` — `make` and `OffDevice` need the class's
  `publishes` either way).
- **To reverse.** `Server` is forty lines.
- **Rough edge.** macOS asks once whether "Python" may accept incoming network connections the
  first time a server binds `0.0.0.0`; deny it and the phone's messages never arrive (the line
  stays `lost`). `hyperspace.osc` is imported whenever the registry looks up a kind, even with
  no OSC entry (the library is not).
- **Judge it.** Checks W.B4.1, W.B4.4.

### 1xx. `devices.PointCloud`: read-only float32 N×3, the frame clock's `t`, a counting frame id, a bounds box, optional colours

- **Built.** `PointCloud(points, t, frame, colors=None)`, a frozen dataclass: `points` N×3
  float32, C-contiguous and **read-only** (the buffer `ctx.buffer(cloud.points)` uploads as it
  is; nobody downstream may write it; a caller's own writeable array is copied, a read-only file
  slice is shared), `t` the frame clock's `now` when the frame was published (monotonic
  seconds, the clock the registry polls with), `frame` an id counting up from 0 while the device
  is open (a reader uploads only when it changed), `bounds` a read-only 2×3 float32
  `[[xmin, ymin, zmin], [xmax, ymax, zmax]]` (zeros for an empty cloud), `colors` None or N×3
  float32 RGB 0–1, read-only. `n` is the point count. Units are the publisher's (the file's;
  plan 29's sensors' metres).
- **Other options.** (a) `t` as the recording's own time (A4b would have to know each source's
  epoch). (b) `frame` as the index into the file (repeats on a loop: a reader cannot tell a new
  frame from an old one). (c) Points as N×4 (homogeneous, or with a size) — the hands' and the
  shape's vertex layouts are xyz.
- **To reverse.** One dataclass.
- **Rough edge.** A skipped id means the source ran faster than the app polled (12 fps never
  does at 60 Hz). **Points are expected finite**: a NaN point gives NaN `bounds` (`min`/`max`);
  plan 29's sensor devices must filter invalid depth pixels before publishing, or `bounds`
  moves to `nanmin`/`nanmax`.
- **Judge it.** Check W.B4.5 (and A4b's own check, when it draws it).

### 1xx. Clouds are on the registry, not the Router: `DeviceRegistry.clouds` as `cloud:<role>`

- **Built.** A device that publishes a cloud holds its latest frame in `cloud`; the registry's
  `clouds` property maps `cloud:<role>` → that frame for every **open** device that has one, in
  list order — what A4b's point-cloud node reads (it names the source `cloud:scan`). Nothing
  reaches the Router: no `cloud` scheme in `continuous_schemes`, `row_schemes`, `wants` or
  `Router.feeds`. The cloud device's one `Port` has `kind = "cloud"` and `scheme = "cloud"`
  (`address` `cloud:scan`), so the plan 28 editor can draw it. A closed or removed device's
  cloud is gone from the map at once (computed, not stored).
- **Other options.** (a) `Router.feed("cloud", …)` (the Router holds float vectors per scheme;
  a cloud is not one, and every lane reader would have to skip it). (b) A stored dict the
  registry fills in the feed slot (stale after a close unless cleared).
- **To reverse.** One property.
- **Rough edge.** The map is rebuilt on each read (a dict of the devices that have a cloud;
  cheap).
- **Judge it.** Check W.B4.5.

### 1xx. The cloud file: version-1 `.npz` — rate, ragged offsets, concatenated points, optional colours

- **Built.** `write_clouds(path, frames, rate, colors=None)` writes `version` (1), `rate`
  (float, frames per second), `offsets` (int64, F + 1: frame i is
  `points[offsets[i]:offsets[i+1]]`, so frames may differ in size, as a sensor's do),
  `points` (float32, M×3) and, when given, `colors` (float32, M×3) with `np.savez_compressed`.
  `read_clouds` checks every key and shape and refuses another version, offsets that do not walk
  the points, or a rate that is not positive, each as a ValueError the device's line shows. The
  fixture `tests/fixtures/clouds/knot.npz` (31 KB, force-added) is a (2, 3) torus knot turning
  about its vertical axis: 16 frames at 12 fps, 96 + 8 i points on frame i, coloured by height,
  written deterministically by `tools/cloud_fixture.py` (no random numbers, no clock;
  `tests/test_clouds.py` checks the committed file's arrays equal a fresh run's).
- **Other options.** (a) A fixed N per frame (an F×N×3 array — a sensor's count varies). (b)
  PLY / PCD files (a parser to own; no colour convention). (c) One `.npy` per frame in a folder
  (many files, no rate).
- **To reverse.** Two functions; nothing outside the tests reads the format yet.
- **Rough edge.** No per-frame timestamps: a recording is played at one rate. A recorder for
  plan 29 that captures at an uneven rate resamples, or the format gains an optional `times`
  (version 1 readers ignore unknown keys).
- **Judge it.** Check W.B4.5.

### 1xx. The `cloud` device plays at its own rate against the frame clock; `file` is the home's

- **Built.** `[[devices]] kind = "cloud"` with `file` (required; relative to the home), `rate`
  (default the file's), `loop` (default true; false holds the last frame). Polled at `now`, it
  shows recorded frame `floor((now − start) · rate)` (mod the file's length when looping), and
  that count is the cloud's `frame` id — so it plays at 12 fps whatever the app's frame rate.
  `connected` while the file is loaded; a missing or bad file, or a `rate` that is not a
  positive number (`rate = -1`), is `error: …` with one note and the registry retries it, so copying the file in later brings it up with no relaunch. The
  SYSTEM line: `scan · cloud · connected · 1 source · knot.npz · frame 7/16 · 144 points ·
  12 fps`.
- **Other options.** (a) One recorded frame per app frame (playback speed would follow the frame
  rate). (b) Resolve `file` in `config.py` like `tape` (config would name the cloud kind's keys).
- **To reverse.** One class.
- **Rough edge.** The file is read whole at open (the fixture is 31 KB; a long recording would
  want streaming). A changed recording on disk is not re-read until the entry changes or the app
  restarts.
- **Judge it.** Check W.B4.5.
