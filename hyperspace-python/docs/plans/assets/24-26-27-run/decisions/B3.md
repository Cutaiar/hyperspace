## 1. Register-row drafts (`docs/DECISION-REGISTER.md` format; the docs WP numbers them)

### 1xx. The sink row: `{"source": "param:<id>" | "lane:<i>" | "lane:*", "target": "<role>:<channel>", "op": "send"}`

- **Built.** A param (or an analyzer lane) routed *out* is one more row in the one table:
  `Binding(source, target, op="send")` (`routing.SINK_OP`). Its source is `param:<id>` (the
  param's **effective** norm — base + this frame's modulation — read after `reg.apply`), `lane:<i>`
  (the lane as a route reads it, `lane / CEIL`) or `lane:*` (every analyzer lane from the row's
  channel on, as many as the band layout has); its target is a **sink port**, `<role>:<channel>`
  (`bridge:3`, `hands-daw:0`) — a device's `sinks`, a `Port` whose `scheme` is the role and whose
  `name` the channel. It is a **session** row (`is_session_row`: `bindings.json` keeps it — sinks
  are rig, D1 / D9), never a performer (`is_performer` is false: no `Owned`, no Replace / Keep, the
  modulation pass never reads it), never in a preset (`routes()` / the preset signature exclude
  it), and the referee's door checks only its form (`sink_refusal`: a param or lane source, a
  `<role>:<channel>` target). What a sink sends each frame is `routing.sink_values(rows, reg,
  analyzer)` — channel → reading — over the enabled rows on its role (`Bindings.sinks(role)`); a
  row on a channel a `lane:*` also fills wins it. A trigger or an id the registry lacks reads 0
  (what the bridge always sent). In the file: `{"source": "param:view.bright", "target":
  "bridge:3", "op": "send"}` (and `"enabled": false` when switched off on ROUTING).
- **Other options.** (a) A separate `sinks` list in `bindings.json` (a second table, a second
  edit path — the brief says the same table). (b) The op named `sink` or `out` (cosmetic). (c) The
  sink port as the *source* and the param as the *target* (`bridge:3 → view.bright`) — reads like
  a route the wrong way round and every `target`-is-a-param reader (owner, Unbind, `routes_to`)
  would need a sink exception. (d) Store sink rows in the preset — sinks are rig (D1 / D9).
- **To reverse.** `SINK_OP`, `Binding.is_sink` / `sink`, `sink_refusal`, `sink_values`,
  `Bindings.sinks`, the `_check` branch: an hour; a file with `"op": "send"` rows would then fail
  the `_check` of a `param:` source.
- **Rough edge.** A `lane:*` row's width is the live band layout's: with more bands than the
  channels before the next row, the star's later lanes are hidden by that row (an explicit row
  wins its channel). A param's alias (`band.sel.*`) can be sent — it follows the selection.
- **Judge it.** Checks W.13, W.15.

### 1xx. `[bridge] send` becomes sink rows once, the first launch the bridge is on with none

- **Built.** When the registry is built (and whenever `[[devices]]` is re-applied), every
  **enabled** entry with a `send` list — the bridge's, the default `["lane:*"]` included — whose
  role has **no sink row at all** (enabled or not) in the session's table gets the list as rows
  (`routing.sink_rows_from_send`: slot k → `<role>:<k>`, a `lane:*` one row taking the default
  layout's 6 channels before the next entry, as the list did on the default bands), written to
  `bindings.json` with one note on stderr and the SYSTEM page: "bindings: [bridge] send is now sink
  rows in bindings.json (lane:* → bridge:0, param:view.bright → bridge:6) — the rows say from
  here on; edit them on ROUTING (sinks)". From then on the rows say and `send` is not read. An
  entry it cannot translate (`ext:3`) is its own note. An off bridge seeds nothing (a rig that
  never turns the bridge on never gets a write). A `bindings.json` that still holds a preset's
  part (pre-plan-13, awaiting `preset.migrate_home`) is not written early: the rows ride in
  memory and that migration's rewrite keeps them. A `Bridge` made on its own (tests, tools)
  still sends its `send` list through `step` / `transmit`, so the old key keeps working there.
- **Other options.** (a) Translate on every launch from `config.toml` (the key would win over the
  owner's ROUTING edits for ever). (b) Keep `send` as the source of truth and show it as rows
  read-only (two places to edit one thing). (c) Note only when the file wrote `send` (the
  default's translation would then write `bindings.json` silently).
- **To reverse.** `DeviceRegistry._seed_sinks` and `routing.sink_rows_from_send`.
- **Done-mark (fix round 1, orchestrator's ruling).** The translation is marked done in
  `bindings.json` itself, never by consuming the owner's config key: a top-level
  `"sinks_seeded": ["bridge"]` (`Bindings.sinks_seeded`, read by `from_json`, written by
  `to_json` / `dumps_doc` only when non-empty, so a file with none is byte-identical). A role in
  the list is never seeded again — deleting every row on ROUTING, relaunching, or saving
  config.toml mid-session (the registry's re-apply) brings nothing back. A file from before the
  mark that already holds sink rows on a role counts as seeded (the mark is added and written).
- **Rough edge.** Editing `[bridge] send` after the first launch does nothing (the note said so);
  to translate it again, remove the role from `"sinks_seeded"` in bindings.json. An entry after
  `lane:*` in the old list lands at channel `len(BANDS)` = 6 (the default band layout), so on a rig
  with a different band count the far end's channel map shifts against the old list once.
- **Judge it.** Check W.14.

### 1xx. The hands' DAW out is a `midi-out` sink, `hands-daw`; `HandsIO` makes the messages and opens no port

- **Built.** `hands/core.py` no longer opens, reopens or closes a MIDI port: `HandsIO.poll` still
  makes the frame's DAW messages exactly as before (per axis CC / 14-bit / pitch / pressure, the
  presence and pinch notes, rate-limited, `solo`) and returns them, but they wait in
  `HandsIO.outbox` for the frame's carrier — `HandsIO.carry(send, name, error)`, a plain callable
  the device drives — and `HandsIO.resync()` returns the notes that are on (and resets the axes'
  last values) for a port that came back. (A caller with a port of its own — a test, a tool —
  hands it in as `out=`, which is sent to directly and never reopened, as before.) The port moved
  to `bridge.py`: `bridge._open_out` (unchanged), `bridge.OutPort` (find by substring, else make
  a virtual port unless `virtual = false`; after a loss only a port that is back, or a new virtual
  one if the first open made one; looked for again on `midi.retry_after`'s schedule; an open that
  fails said once on stderr). The device is `devices.MidiOutDevice` (`kind = "midi-out"`): in
  `poll` its port is looked for again (and on a reconnect the carried `HandsIO.resync()` runs
  *before* the hands' frame, so the axes resend that frame, notes first); in `send` (after
  `reg.apply`) it sends the resync notes, then `HandsIO.carry(...)`, then any sink rows on its
  role (encoded like the bridge's lanes: `encoding` / `channel` / `cc` / `rate`, default pitch
  from channel 0, `bridge.Sender`). It finds the hands device through `Context.devices` (the
  registry) by the role its `carries` key names. **`[hands] out` keeps working**: at config load
  the first enabled hands entry (the old table translated, or a `[[devices]]` hands entry) whose
  `out` is non-empty gets an entry right after it — `role = "hands-daw"`, `kind = "midi-out"`,
  `port = <out>`, `carries = <hands role>` — unless the list already has a midi-out carrying that
  role; one note when the file wrote `out` itself, none for the default port (today's behaviour).
- **Other options.** (a) Keep the port inside `HandsIO` and have the sink only "own" it (the
  brief: core no longer opens a MIDI port). (b) Move the whole DAW encoding out of core (it reads
  the axes' settings and shaping state; it is the instrument's, and `hands/` must stay liftable —
  a liftable instrument that makes its MIDI is more useful than one that cannot). (c) Put
  `OutPort` in `midi.py` (not B3's file; `bridge.py` is already the gated "MIDI out" module). (d)
  Send from the hands' feed slot (before `reg.apply`): the brief puts sinks after apply.
- **To reverse.** Put `_open` / `_send` / the reconnect fields back into `HandsIO` (the old
  code is the `OutPort` body), drop `_daw` in config and the kind.
- **Rough edge.** The DAW messages now leave in the sink slot, after `reg.apply`, the same frame
  — about a millisecond later than before. A rig that lists the hands **off** gets no
  `hands-daw` entry; turning the hands on by a live `[[devices]]` edit derives it on the re-read.
  Tools that build a `HandsIO` with no `out` (preset_shots, golden_frames) no longer make a
  "Hyperspace Hands" virtual port as a side effect. `tools/hands_probe.py` carries its DAW out
  through an `OutPort` itself.
- **Judge it.** Checks W.16, W.17.

### 1xx. "Learn sink ▸ <role>:<channel>" on the param menu lands at once, in the session

- **Built.** The param's right-click menu gains **Learn sink ▸** (beside Learn desk / hand ▸ /
  pad / <role>), listing every sink port the rig's devices offer (`DeviceRegistry.sink_ports`,
  `Learn.sinks`, `ui.sink_items`: `bridge:3  ·  pitch ch4`), on any param but a trigger. A pick
  lands immediately — there is nothing to wait for — through `Learn.learn_sink(pid, port)`: a sink
  row `param:<pid> → <port>` added to the table and `bindings.json` written now, like Learn pad
  (session rows: no undo step, no preset dirt). It replaces whatever sent on that port before
  (one source per port; the footer names what was let go); a param may go out on several ports.
  No Replace / Keep, ever: a sink row is not a performer, the param's performer is untouched.
  Refused (in `last`, nothing changed) for an id the registry lacks, a trigger, a port that is not
  `<role>:<channel>`. The menu's bound lines list the param's sink rows dim ("→ bridge:3 · sink"),
  and Unbind never removes them (session rows, D5/D6's rule). The rows show on ROUTING in their
  own **sinks** section after the session's (a checkbox and a ×, both writing the file; the filter
  finds them).
- **Other options.** (a) Arm-and-wait like the other learns (nothing on a sink moves to complete
  it). (b) A sink picker page (the brief: no new page or picker). (c) An undo step (the session's
  rows are not undoable today — pad learns are not either).
- **To reverse.** `Learn.learn_sink` / `sinks`, `ui.sink_items`, the menu block, `ui_routing.sinks`.
- **Rough edge.** A sink device that is `off` offers no ports (an off device has no adapter to
  ask its encoding), so nothing can be learned onto it until it is on. The list is long (16 per
  pitch-encoded sink).
- **Judge it.** Check W.15.

### 1xx. The bridge is one device with two halves; `ext` publishes its labels and rests; `N_EXT` is gone

- **Built.** `BridgeDevice.poll` → `Bridge.reconnect()` (the ports looked for again, scene-setter
  slot); `feed` → `Bridge.receive(router)` + `Bridge.publish(router)` (the `ext` vector, and
  `labels["ext"] = ["ext 0" …]`, `rests["ext"] = [0.0] * in_lanes`); `send` (after `reg.apply`) →
  `Bridge.send_values(sink_values(table.sinks(role), …))`. The outbound gate is `bridge.Sender`
  (per channel: quantise, change-gate, rate-limit, encode; `reset` on a reconnect), shared with
  `midi-out`. Param lanes are therefore sent with this frame's effective value — no longer one
  frame behind. `ui_routing.N_EXT` is gone: the ROUTING combo offers the lanes the bridge
  publishes, and for a scheme nobody publishes, up to the highest lane a row names. The labels
  read "ext 0" (so `Router.describe` still says "ext 3 pushes …", as before).
- **Other options.** Labels as the wire ("pitch ch4") — would change every ext route's words.
- **To reverse.** `Bridge.publish` and the `n = …` line in `_sources`.
- **Rough edge.** The combo reads "ext ext 0" (scheme then label), as LFOs read "lfo LFO 1".
- **Judge it.** Check W.14.

### 1xx. A sink's SYSTEM line starts its last part with `n sinks`

- **Built.** `DeviceRegistry.lines()` prefixes the last part of any device that has sink ports
  with the number of **enabled sink rows** on its role: `bridge · bridge · connected · 16 sources ·
  2 sinks · IAC Driver Bus 1 · pitch, 16 lanes · 41 sent`; `hands-daw · midi-out · connected · 0
  sources · 0 sinks · Hyperspace Hands · leap's DAW out · cc 102 = 64 ch16` (the port, what it
  carries, the last message). The line tuple keeps B1's five fields.
- **Other options.** A sixth tuple field (every caller and test of `lines()` changes); counting
  sink *ports* (16 for any pitch bridge — says nothing about what it sends).
- **To reverse.** Four lines in `lines()`.
- **Rough edge.** `hands-daw` reads `0 sinks` while it carries the hands' messages — the carry is
  in the words after it.
- **Judge it.** Checks W.14, W.16.

## 4. What a document says that the code does not do, or what was deliberately not done

- The brief's "Learn arms a sink port": the pick **lands** at once (nothing on a sink moves to
  complete an armed learn); no `want` is added to `Learn.wants`.
- The DAW encoding stays in `hands/core.py` (the instrument makes its messages); only the port
  moved out (to `bridge.OutPort`) — "a plain callable the device drives" is `HandsIO.carry`.
- `docs/ARCHITECTURE.md` §2's frame table (the bridge "feeds ext and sends lanes"; the hands "send
  the DAW MIDI" in their poll) and §3's source list (no `param:` scheme) are stale — B5's.
- `[bridge] send` is read only for the first translation; afterwards the key is dead text (said in
  the note and in config.py's docstring), not removed from DEFAULTS (a `Bridge` made on its own
  still uses it).
