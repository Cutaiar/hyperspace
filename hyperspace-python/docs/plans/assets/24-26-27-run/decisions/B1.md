## 1. Register-row drafts (`docs/DECISION-REGISTER.md` format; the docs WP numbers them)

### 1xx. `[[devices]]`: the rig's devices as a list of tables, the old tables translated

- **Built.** `config.toml` may list the rig's devices as `[[devices]]` tables, each with
  `role` (a name without `:`, unique), `kind` (`midi`, `gamepad`, `hands`, `bridge`; B3 adds
  `midi-out`, B4 `osc` and `cloud`), `enabled` (default true) and the kind's own keys — exactly
  the keys the old `[midi]`, `[gamepad]`, `[hands]` and `[bridge]` tables hold, with the same
  defaults. **A config with no list keeps working unedited:** the four old tables (the defaults
  and what the file says) become the equivalent entries at load, in today's poll order — `pad`
  (gamepad), `apc40` (midi), `leap` (hands), `bridge` (bridge) — with one note per table the
  file holds ("config: [midi] is now a [[devices]] entry (role = 'apc40', kind = 'midi') — see
  config.py"), on stderr and the SYSTEM page, like `[overlay] is now [output]`. With a list,
  the list says: the old tables are ignored with a note each. The first entry of each old kind
  is folded back into its table, so `cfg["midi"]` (the binding file's profile and map) and
  `cfg["hands"]` (the hands setup, `migrate_home`) say what the entry says. A relative `map`,
  `calibration` or `tape` resolves against the file's folder in both. An entry with a bad or
  duplicate role, or no kind, is dropped with a note; `enabled` that is not true/false is true;
  an unknown kind is kept for the registry to show as `error: unknown kind`. The owner's rig as
  a list:

  ```toml
  [[devices]]
  role = "pad"
  kind = "gamepad"

  [[devices]]
  role = "apc40"
  kind = "midi"
  port = "APC40"

  [[devices]]
  role = "leap"
  kind = "hands"
  enabled = false

  [[devices]]
  role = "bridge"
  kind = "bridge"
  enabled = false
  ```
  (`tests/test_devices.py::test_todays_rig_as_a_devices_list_equals_the_old_tables`.) `[dream]`
  stays a table: the dream worker is not a device — it has no sources and no sinks and is
  polled by the renderer's look-back, not the frame — so it keeps `app._open_dream` and its
  place after the registry on the close list.
- **Other options.** (a) A `[[devices]]` list only, the old tables an error (breaks every rig
  config, the owner's `config.toml.rig` included). (b) Translate silently (the file never
  catches up; two ways to say one thing for ever). (c) Roles `midi` / `gamepad` / `hands`
  instead of `apc40` / `pad` / `leap` (the prompt's examples name the device on the stage;
  `apc40` is also what the desk page and the rows already mean).
- **To reverse.** `config._translate` and `config.DEVICE_TABLES`; the notes are strings.
- **Rough edge.** Every launch of an un-renamed rig config prints four notes (one per old
  table present) — by design, until the file is edited. A list with no `hands` entry marks
  `cfg["hands"]["enabled"] = False` but the hands *settings* still register from the defaults
  (as today with no `[hands]`), so the HANDS page says "tracker off".
- **Judge it.** Check W.1 and W.2.

### 1xx. Role ≠ scheme for today's devices; `Device.schemes` maps them; one scheme, one enabled device

- **Built.** The prompt's "the role is the scheme" holds for a *new* device (B4's OSC
  publishes under its role) but not for today's four: their rows already name schemes the
  adapters own — `axis` / `pad` / `hat` (the pad), `hand` (the hands), `ext` (the bridge),
  `cc` / `note` / `pitch` (MIDI) — and the prompt's own role examples are `apc40`, `pad`,
  `leap`, which B2's MIDI qualifier (`cc@apc40:…`) needs as a role distinct from `cc`. So an
  entry's `role` names the device (the SYSTEM line, the notes, B2's qualifier) and the
  device class's `schemes` tuple says which Router keys that role publishes; a preset names a
  scheme, and every existing row is unchanged whatever the entry is called. `feeds` is the
  subset of `schemes` the device feeds continuous vectors under (`axis`, `hand`, `ext`; MIDI
  none), and `DeviceRegistry.continuous_schemes()` lists `lane`, `lfo` then each listed
  device's `feeds` in list order — what B2 hands the Router in place of `LANE_SCHEMES` /
  `SOURCE_ORDER` (an `off` device's scheme is listed too, so a row naming it stays dormant).
  Every `Port` carries its `scheme` and `address` (`scheme:name`: `axis:LX`,
  `hand:right.roll`, `cc:0:48`), so plan 28 builds a cable from a port. **The hazard this
  leaves — two enabled `hands` or two `gamepad` entries feeding the same Router key, the
  later overwriting the earlier every frame while the fold-back and `adapter(kind)` see only
  the first — is closed in `devices.make`, per fed scheme and per role:** a second enabled
  entry whose class would **feed** a scheme (`feeds`) an earlier enabled entry already feeds
  becomes a `RefusedDevice` (`error: feeds 'axis', which pad already feeds — not opened`),
  never opened, one note naming both roles, in effect `enabled = false`; it comes up when the
  first leaves the list (`apply` re-makes the list). A kind that feeds nothing is never
  refused: MIDI's messages are rows, so two desks of different roles (`apc40`, `launchpad`)
  both open — exactly what B2 builds, qualifying rows by role. One role, one entry: config
  drops a duplicate role (at load and on a re-read). `off` entries claim nothing.
- **Other options.** (a) Make the role the scheme for today's devices too (every preset row
  and `bindings.json` rewritten to `leap:right.roll`, `pad:LX`; the prompt forbids it).
  (b) Let the last entry win silently (the Router's `feed` overwrites). (c) Refuse in
  `config._device` (config does not know a kind's schemes; the registry's kind table does,
  and B4's OSC kind must be refusable without a config change).
- **To reverse.** `Device.schemes` / `feeds` are class tuples; `RefusedDevice` and the
  `claimed` dict in `make` are twenty lines.
- **Rough edge.** A refused entry is an `error:` line, not `off`, so the owner sees why; its
  fold-back into `cfg["midi"]` / `cfg["hands"]` still takes the *first* entry of the kind
  (the one that is open) — consistent. Until B2, two MIDI desks both open but their rows
  are unqualified (`cc:0:48` means either), so a knob on one moves what the other's row
  names — B2's qualifier settles it. Whether the pad's **row** schemes (`pad`, `hat`) should
  also block a second pad — two pads' button rows both act today, last press wins, no
  overwrite — is B2's call; the guard is on fed schemes only.
- **Judge it.** Check W.7.

### 1xx. The `Device` protocol: open / poll / learn / act / feed / send / close, ports, status words

- **Built.** `devices.Device` (a `runtime_checkable` Protocol) — `role`, `kind`, `schemes`
  (the Router keys the device publishes under), `layers` (empty until B2), `status`, `last`,
  `sources` (a tuple of `Port`), `open()`, `poll(dt, now)`, `learn(learn) -> bool`,
  `act(router)`, `feed(router)`, `send(reg, analyzer)`, `close()`, `targets()`. `Port` is
  `(name, label, kind="value"|"trigger", rest, bipolar, velocity, group, layer)`: the port
  **is** the node-editor description (plan 28), there is no second one. The two signal kinds
  stay distinct: values feed, triggers are rows. `Base` gives every member a default so a
  device implements only what it has. The registry's frame slots: **scene-setter slot** —
  for each open device `poll` (the hardware read; MIDI applies its rows here), then `learn`
  (offer a moved axis or pressed button to the armed Learn; True when a press was the
  learn's), then `act(router)` (deliver the rest of the frame's rows — the pad's
  `router.pad(pad, buttons=not taken)`); **feed slot** (after `audio.publish`, before the
  LFOs) — `feed(router)`; **sink slot** (after `reg.apply`) — `send(reg, analyzer)`, empty
  until B3. Status is one of `connected`, `lost`, `off`, `error: <why>`: `lost` means the
  hardware is not there and the adapter is looking for it itself (`midi.Ports.retry`, the
  pad's GLFW poll / USB rescan, the hands' DAW port); `error` means the device's own code
  failed (its `open`, or a step this frame). **Whose job reconnect is:** the registry retries
  only an `open` that *raised*, on the Ports schedule; a device whose `open` returned and
  reports `lost` reconnects itself on its own schedule — today's adapters do (`midi.Ports.retry`
  inside `MidiIO.poll` and `Bridge.step`, the pad's GLFW poll and USB rescan, the hands' Leap
  thread and DAW port) and a B2 / B4 device must too (a `Ports` of its own inside `poll` is the
  pattern); the registry never closes or reopens a `lost` device
  (`tests/test_devices.py::test_the_registry_retries_a_failed_open_and_a_lost_device_reconnects_itself`).
  A raising `poll` skips that device's `learn` and
  `act` for the frame; the error stands on its line until the next clean poll; the registry's
  `error` (the first this frame, kind-prefixed as today: `midi: RuntimeError: boom`) goes to
  the hot-reload toast through `reloader.runtime_error`, exactly as the per-adapter `try`
  blocks did.
- **Other options.** (a) `poll(dt, now, router, learn)` as one call (what `HandsIO.poll` is
  today) — rejected so a device that only feeds, or only sinks, implements one method and the
  registry owns the slot order. (b) A separate `rows(router)` name for `act` — same thing.
  (c) Status as an enum — strings are what the page prints and what tests read.
- **To reverse.** The protocol is one class; the registry's three methods are the slots.
- **Rough edge.** `learn` and `act` are two steps the frame-order test can see but a
  device's user cannot; `act` exists only for the pad until B2 (MIDI applies rows inside its
  `poll`, the hands complete a Learn inside the feed-slot call).
- **Judge it.** Check W.3 (a device that raises).

### 1xx. Thin shims over today's adapters; the hands' one call stays in the feed slot

- **Built.** `MidiDevice`, `PadDevice`, `HandsDevice`, `BridgeDevice` own a `MidiIO`, `Pad`,
  `HandsIO`, `Bridge` built in `open()` (the lazy import lives there, so `import
  hyperspace.app` imports none of `midi`, `bridge`, `dream`, `osc`, `leap`, `torch`,
  `pythonosc`) and delegate: the pad's `poll` → `Pad.poll()`, `learn` → `gamepad.learn_from`,
  `act` → `Router.pad`; MIDI's `poll` → `MidiIO.poll()` (rows and desk Learn inside, as
  today); the bridge's `feed` → `Bridge.step(chain if audio.on else None, router)` (in and
  out at once, as today — B3 splits the out half into `send`); **the hands' `feed` →
  `HandsIO.poll(dt, learn, router)`** with the `dt` from `poll` and the Learn from `learn`,
  because that one call reads the tracker, sends the DAW MIDI, feeds `hand` and completes a
  hand Learn together and `hands/core.py` is not touched in B1 (`tests/test_hands_boundary.py`
  untouched; the shim lives in `devices.py`, B2 moves it to `hands/device.py`). So the hands
  still run where they ran — the feed slot — only now after `output.apply` / `mouse.poll` /
  `audio.step` instead of before them; nothing in between reads the `hand` feed. The sticks'
  camera job stays in `app.frame`, reading `Host.pad` (a property over the registry), and
  now runs after every device has polled (pad rows, then MIDI rows, then the sticks) — all
  base writers of independent params. `Pad.close()` is real: the USB reader thread is told to
  stop and joined (≤ 0.5 s), the pad reads absent until a later poll finds one. `MidiIO`,
  `Pad`, `HandsIO`, `Bridge` keep being the objects the panel holds (`panel.midi`,
  `panel.pad`, `panel.hands`) and the ghost renderer reads (`renderer.ghost.source`): a
  registry listener re-points them whenever the list changes.
- **Other options.** Convert the adapters now (B2's job; C1 and C4 are editing them beside
  this WP).
- **To reverse.** Delete the four shim classes when B2 lands the real devices.
- **Rough edge.** The MIDI shim's `sources` are the profile's `LAYOUT` (137 APC40 controls)
  with no role identity in their names yet; the bridge's are `in_lanes` unlabeled `ext`
  ports — labels and rests reach the Router only in B3.
- **Judge it.** Checks W.1, W.4.

### 1xx. The registry: open behind the entry, retry a failed open on the Ports schedule, one close list, listeners

- **Built.** `DeviceRegistry(entries, ctx, path=, clock=, notes=)` makes one device per
  checked entry (`make`: `OffDevice` for `enabled = false` — listed as `off`, never opened,
  nothing imported; `UnknownDevice` for a kind the table lacks — `error: unknown kind 'x'`,
  one note). `open_all()` opens each; one whose `open` raises is `error: …`, said once on
  stderr and in the config notes (`"<kind>: <error>"` — the same text as the old `_open_*`
  gates, so the HANDS page's "hands: " rule holds), and tried again on the Ports schedule —
  `retry_after(misses)`: 2 s for five misses, then every 10 s (`tests/test_devices.py` holds
  it equal to `midi.retry_after`) — the moment it opens it is polled from that frame and the
  listeners run. `close()` closes every device last-listed-first, best-effort (a raising
  close is a note, its adapter is let go of); `Host.adapters == (devices, dream_io)` is the
  one close list for a quit and ⌘R, the pad now on it. `adapter(kind)` gives the first open
  adapter object of a kind, `get(role)` a device, `first(kind)` the first listed device,
  `schemes()` every scheme in list order (what B2 feeds the Router), `lines()` the SYSTEM
  page's tuples, `targets()` the hot reloader's swap targets (the registry, each shim, each
  adapter: `(midi_io, "midi", "MidiIO")` and so on, re-evaluated each swap).
- **Other options.** (a) Retry inside each device (every device re-implements the clock).
  (b) Close in list order (the bridge, which sends what the others produce, is now closed
  first — last opened, first closed).
- **To reverse.** The schedule is three constants; the close order one `reversed`.
- **Rough edge.** A device that raises on `poll` every frame (a hot-reload bug) is never
  closed and reopened — it is red on its line and the toast until the file is fixed, as the
  per-adapter guards did; the Ports schedule covers only a failed `open`.
- **Judge it.** Checks W.3, W.5.

### 1xx. The config list is watched by mtime every 30 frames; a bad edit keeps the old list

- **Built.** `DeviceRegistry.poll` counts frames and every `WATCH_FRAMES = 30` (the shaders'
  cadence) stats `<home>/config.toml`; when the mtime moved, `config.read_devices(path)`
  re-reads the file (nothing printed) and gives the checked entries plus every *problem* (a
  parse error first, then each entry that had to be dropped). Any problem: one note
  ("config: [[devices]] not applied — <problem> — the old list stands"), nothing changes. No
  problem: `apply(entries)` — an entry whose dict is unchanged keeps its device; a changed
  one is closed and opened again ("devices: apc40 changed — reopened"); a new role is opened
  ("added"); a role that left is closed ("removed"); the order becomes the list's; the
  listeners run. A file with no `[[devices]]` re-reads as the old tables translated, so
  flipping `[hands] enabled` in the old form lands too. The registry's notes are
  `cfg["notes"]` itself, so the SYSTEM page shows them (and `panel.config_notes` is now that
  very list; `router.table.said` is appended to it rather than copied).
- **Other options.** (a) Reload the whole config (the outputs, the library path and the
  windows are not hot-pluggable; the prompt says the list only). (b) Apply the good entries
  of a partly bad edit (a half-applied list is harder to reason about than "fix the line and
  save again").
- **To reverse.** `watch` / `apply` are two methods; `WATCH_FRAMES` one constant.
- **Rough edge.** A changed entry is reopened even when the change is cosmetic (a comment
  does not count — only keys and values — but reordering keys in the file does not either;
  `enabled = true` written explicitly equals the default). A reopen of the MIDI device
  re-sends the profile's `enter` and redraws the desk. An editor that writes the file in two
  steps may land a parse error first (a note) and the good list 30 frames later (applied).
- **Judge it.** Check W.6.

### 1xx. The SYSTEM page: one line per device

- **Built.** A `devices` section before `midi`: for every listed device, in list order,
  `role  ·  kind  ·  status  ·  n sources  ·  last` (`last` only when the device has one:
  MIDI's **port name and the table's binding count, then the last message once one has
  come** — `apc40 · midi · connected · 137 sources · Akai APC40 · 160 bindings · cc 0 48 =
  64`, so nothing the old MIDI line showed is lost; the pad's road and USB name or the USB
  note; the hands' last DAW message or tracker status; the bridge's ports / encoding / lanes
  / sent count) —
  `error: …` lines in the warning colour. "no device registry" with none, "no devices —
  [[devices]] in config.toml" with an empty list. `_midi_status` and `_bridge_status` are
  gone (knob smoothing, the Learn line and the pad feel stay in their sections); the HANDS
  page keeps its own status line. `ui.device_lines(registry)` is the pure text (tests), the
  drawing is `Panel._device_lines`, its own helper so A0's per-pass timing lines merge
  cleanly.
- **Other options.** Keep the old two lines beside the new ones (two places to read one
  thing).
- **To reverse.** One helper.
- **Rough edge.** `lost` is drawn in the normal (dimmed) colour: at the machine with no desk
  plugged in it is the expected state, not a warning. A line can be long when the bridge is
  up (ports, encoding, lanes, sent).
- **Judge it.** Check W.1.

## 4. What a document says that the code does not do, or what was deliberately not done

- The prompt's "the role is the scheme" is built for new devices only; today's four keep
  their schemes behind `Device.schemes` (row above) — a conscious deviation, with the
  refusal that closes the hazard it opens.
- The prompt's "`sources` (continuous axes: name, label, rest, bipolar; hits: name, label,
  with velocity)" is one `Port` type with `kind`, `velocity`, `scheme` and `address` rather
  than two types: one description for the node editor, and a cable from a port.

  registry calls after it (the pad needs `learn` before its rows; MIDI and the hands do both
  inside their one call). B2 may fold `act` into `poll` for the real pad device.

  after every device polled, not between the pad and MIDI.

  content is all there.
