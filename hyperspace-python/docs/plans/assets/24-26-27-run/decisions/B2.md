## 1. Register-row drafts (`docs/DECISION-REGISTER.md` format; the docs WP numbers them)

### 1xx. A second MIDI desk's rows are `cc@<role>:<ch>:<n>`; an unqualified row is the first MIDI role's

- **Built.** Every `[[devices]]` MIDI entry is its own desk. The **first MIDI role listed** reads
  the unqualified rows — every row in `bindings.json` and in every preset written before plan 27
  (`cc:0:48`, `note:0:98`, `pitch:0`) — so nothing moves. Any other MIDI role's rows carry its
  role after `@` on the kind: `cc@launch:0:21`, `note@launch:0:40`, `pitch@launch:3`. The
  qualifier adds no `:`, so everything that splits a source at its first `:` (the router's lane
  cache, the hand-name map, the ROUTING page) is untouched. `Binding.scheme` is the bare kind
  (`cc`), `Binding.device` the role, `Binding.bare` the source without it (what a profile names);
  `midi_source(kind, ch, n, role)`, `overlaps` (same device too), `describe` ("MIDI CC 21 ch1 on
  launch") and the table (`serves`, `role_of`, `dispatch(…, role)`, `active(role)`) know it.
  Learn desk on the second desk writes the qualified form for you (`MidiIO.qualifier`). The
  registry tells the table the roles in list order (`Bindings.midi_roles`) before any desk opens.
- **Other options.** (a) `<role>:cc:<ch>:<n>` — adds a `:` and breaks every first-`:` split.
  (b) `cc:<role>/<ch>:<n>` — puts the device inside the channel field, which `channel` parses.
  (c) Qualify every row, the first desk's too — rewrites every preset and `bindings.json`
  (the prompt forbids it). (d) Make the role the scheme (`launch:cc:0:21`) — same `:` problem.
- **To reverse.** `routing.QUALIFIER` / `base_scheme` / `Binding.device` / `bare` and the
  table's `serves`: an hour; nothing on disk uses the form until the owner learns on a second
  desk.
- **Which role owns the unqualified rows (orchestrator's ruling, review of PR #181).** The
  first MIDI role whose `profile` equals the binding table's (`bindings.json`'s `"profile"`,
  `apc40` by default) — the desk the file's rows were written for — else the first MIDI role
  listed (`DeviceRegistry.midi_roles` puts that role first). So a generic box listed above the
  APC40 does not inherit the APC40's factory rows or SHIFT, and a rig whose only desk is generic
  still maps (`tests/test_device_inputs.py::test_the_desk_whose_profile_wrote_the_table_owns_the_unqualified_rows`).
- **Rough edge.** A hand-written `cc@apc40:…` (the owning role named explicitly) dispatches as
  that role's but is a different control from its unqualified twin to `overlaps` /
  `is_invariant`, so a learn next to it would not replace it and an invariant twin would not
  shadow it (normalising such rows at load would close it). Two APC40-profile desks: the first
  listed owns the unqualified rows.
- **Judge it.** Checks W.8, W.9.

### 1xx. The SHIFT latch is per MIDI role; `desk.shift` is the first role's; a second desk has none

- **Built.** `Bindings.layer` stays the first MIDI role's layer — the one `desk.shift` reads
  and SHIFT's invariant row toggles — and every other role has its own in `Bindings.layers`
  (`layer_of(role)`, `set_layer(layer, role)`, `toggle_layer(role)`), the preset layer until
  something latches it. `dispatch` / `active` read the role's layer; Learn's `blocked` refuses
  only on the control's own desk's global layer (D5), so with the APC40 on SHIFT a knob on the
  second desk still learns into the preset and its rows still act. A preset load drops **every**
  desk to the preset layer (D4). D12 is per desk (each `MidiIO` keeps its own press → rows).
  SHIFT's own note is special only on the first role's desk. `MidiDevice.layers` says which
  layers a desk exposes for plan 28's one-node-per-mode: `("preset", "global")` for the first
  role's APC40, `("preset",)` for any other desk.
- **Other options.** (a) One layer for every desk (the B1 state: the APC40's SHIFT would blank
  the second desk's preset rows). (b) A latch param per role (`desk.<role>.shift`) and a SHIFT
  row on each APC40-profile desk — a second APC40 would need its own factory rows too; deferred
  (the prompt: "a second desk has its own, or none").
- **To reverse.** `layers` / `layer_of` and the `role` argument on four methods.
- **Per-desk serial (review of PR #181).** Each role's layer changes are counted on their own
  (`Bindings.layer_serial_of(role)`; the first role's is `layer_serial`), and each `MidiIO`
  follows only its own (`_serials`), so C2's switch-time pickup re-arm (`redraw(switch=True)`)
  runs only on the desk whose latch flipped (D7 per control, per desk):
  `tests/test_device_inputs.py::test_shift_on_the_apc40_leaves_the_second_desks_caught_rows_caught`.
- **Rough edge.** A second **APC40** (profile `apc40`, not the owner of the unqualified rows)
  gets its power-up SysEx and the rings / LEDs of its own qualified rows, but no SHIFT of its
  own: its SHIFT button is an ordinary unmapped note, its global-layer rows never act.
- **Judge it.** Check W.9.

### 1xx. The `generic` MIDI profile: plain CC / note / pitch, no feedback, a `port` required

- **Built.** `hyperspace/generic.py`, a profile module beside `apc40.py`: `PORT_MATCH = None`
  (the entry must name its `port`; without one the line reads `error: ValueError: the generic
  profile matches no port by itself — give the entry a port …`, never the first port that happens
  to be there), `FEEDBACK = False` (MidiIO sends the device **nothing**: no power-up, no ring, no
  LED, no leave), every CC absolute with soft pickup, a note a toggle, pitch an absolute 14-bit
  fader (what Learn makes with no profile), no layout (the device line counts 0 sources; the
  on-screen desk stays the APC40's), no factory rows. A `profile` the registry does not know is
  an error line (`no MIDI profile 'akai'; one of apc40, generic`). `bindings.json`'s top-level
  `"profile"` says only which profile the file's unqualified rows were written for (the apc40
  role's): `MidiIO` takes the **entry's** profile, the file never overrides it.
- **Other options.** (a) Echo values back as CC (many generic boxes have LED rings that follow
  input) — a controller that echoes what it receives would loop. (b) Let a generic entry with no
  port take the first port — would grab the APC40. (c) Separate "generic pads" / "generic CC"
  profiles as the brief's wording suggests — one profile covers both; split when a device needs
  it.
- **To reverse.** One module, one `PROFILES` entry, one `_send` gate.
- **Rough edge.** A relative encoder on a generic box learns as `abs` (no profile to say
  otherwise); edit the row's op to `rel` / `rel64` on the ROUTING page.
- **Judge it.** Check W.8.

### 1xx. Continuous is "not a row kind the table dispatches"; the registry says which schemes exist and in what order

- **Built.** `routing.LANE_SCHEMES`, `ui_routing.SOURCE_ORDER` and `learn.WANTS` are gone. A row's
  shape is judged by `routing.is_continuous(scheme)` — anything but `key`, `pad`, `hat`, `cc`,
  `note`, `pitch` (`ROW_SCHEMES`, the kinds the table itself dispatches) — so `is_performer`,
  `to_json`, `describe`, the v1 migration and a preset's route filter need no list, and a preset
  row on a device this rig lacks (`osc:3`, `wand1:tilt`) is a **dormant performer**, never
  dropped (decision 11). *Which* continuous schemes exist and in what order a page offers them is
  the registry's: `Router.use(registry)` (an argument — routing imports nothing new;
  `test_routing_boundary` untouched), `Router.schemes()` = `continuous_schemes()` (`lane`, `lfo`,
  then each listed device's feeds in list order) then anything else fed or labelled this run; the
  ROUTING page's source combo (`ui_routing.source_schemes`) adds any scheme a route names. The
  referee's "a lane takes only push / position" (`_check`) uses `Bindings.row_schemes`, which the
  registry extends with its devices' non-fed schemes (`DeviceRegistry.row_schemes`), so a later
  device that delivers hits as rows under its own scheme is not refused. With no registry (a bare
  router, the tests'), `lane` and `lfo` then whatever has been fed.
- **Other options.** (a) Keep a tuple and have the registry append to it (a module-level global
  every test would have to reset). (b) Make `is_performer` ask the registry (a `Binding` has no
  table; every preset load before the registry exists would drop rows). (c) Keep `SOURCE_ORDER`'s
  order (`hand` before `lfo`) — the prompt puts `lane` and `lfo` first.
- **To reverse.** `is_continuous` back to a tuple test: minutes; `Router.schemes` back to a tuple
  for the page: minutes.
- **Rough edge.** `is_continuous` is open-ended on purpose (decision 11): a typo scheme in a
  preset route (`hnad:right.roll`) is kept as a dormant performer rather than dropped with a
  note. `tests/test_presets.py`'s factory-route check is weaker than the old tuple test for the
  same reason; a stricter check would assert the factory routes' schemes are in a default
  registry's `continuous_schemes()` (not done here).
- **Rough edge.** The ROUTING page's source combo now lists LFO 1–4 before the hands and the pad
  (registry order: `lane`, `lfo`, then `pad`'s `axis`, `leap`'s `hand` / `hands`, the bridge's
  `ext`, as the config lists them). `ext` still has its fixed 16 lanes until B3 publishes labels.
- **Judge it.** Check W.10.

### 1xx. What a Learn can be armed for is each device's `wants`; "desk" is always there

- **Built.** `Device.wants` (protocol): `MidiDevice` `("desk",)` — one want for every MIDI role,
  so a desk learn completes from whichever desk moves first —, `PadDevice` `("pad",)`,
  `HandsDevice` `("hand:left", "hand:right")`, the bridge none, a **new device that feeds** its
  role by default (`Base.wants`). `DeviceRegistry.wants()` lists them in list order, off devices

  scheme". The param menu keeps its three items (Learn desk / hand ▸ / pad, each on its old
  condition) and adds "Learn <role>" for any other want (`ui.learn_wants`). A Learn handed no
  registry offers today's four (`learn.BARE_WANTS`).
- **Other options.** (a) `desk@<role>` per MIDI device (the brief's "desk for every MIDI role"
  read literally per role) — the owner then has to say which desk before touching it; one
  "desk" want lets any desk complete, and the row says which. (b) Only open devices' wants —
  arming would raise while a device is lost for a second.
- **To reverse.** One property per class, `DeviceRegistry.wants`, `Learn.wants`.
- **Rough edge.** A new device's "Learn <role>" item shows on every modulatable param, and only
  that device's own `learn` completes it (B4's OSC device must implement `learn`).
- **Judge it.** Check W.10.
