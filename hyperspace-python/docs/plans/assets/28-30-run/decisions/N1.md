# N1 — modifier nodes, in the preset: decisions, hand checks, as-built

Branch `plan-28-n1-modifiers`, base 5d18192.

## 1. Register-row drafts

**2xx — Each modifier kind's params and curves.**
**Built:** six kinds, each param a registry param `mod.<n>.<p>` (group `mod`, performance, modulatable):
`curve` shape −1…1 (0 straight; y = x^(4^shape), so +1 is x⁴, slow to start, −1 is x^¼, fast to start; input clamped 0…1), invert (toggle, 1 − y);
`scale` mul −4…4 (default 1), offset −1…1 (0), clamp (toggle, **on by default**: the result held in 0…1);
`smooth` attack 0…2 s (0.05), release 0…4 s (0.35), spring (toggle, off) — the follower is `motion.follow` about 0 (attack rising, release falling); spring on is a `motion.spring` with ω = 1/attack and damping 0.6 (release unused); the first reading is taken as it is (no glide in);
`combine` how (enum add · mul · min · max · cross, default add), balance 0…1 (0.5, the crossfade only); add is not clamped;
`threshold` on 0.6, off 0.4 (an off above on is read as on), hold 0…2 s (0.1): 1 on the rising edge's frame and while the hold lasts, then 0; fires again only after falling under off;
`delay` no params: last frame's input, 0 on its first frame.
**Other options:** a curve with an S-shape as well as the exponent; a smooth with separate spring Hz / damping params; add clamped to 0…1.
**To reverse:** small — `modifiers.PARAMS` and the kind functions; a preset holding a param that goes away keeps loading (unknown keys are ignored).
**Rough edge:** a spring smooth has no release; a combine `add` can exceed 1 (a `position` route clamps it, a `push` does not).
**Judge it:** Y.1, Y.2.

**2xx — The `mod` lane's address form and a dormant modifier's reading.**
**Built:** modifier `mod.<n>` publishes lane `mod:<n>` — the lane index is n itself (index 0 unused, labelled "" and never offered). Labels "<n> <kind>" (ROUTING shows "mod 2 combine"), rests 0, a per-lane signal kind (`Router.lane_kinds["mod"]`: "value", or "trigger" for a threshold). A threshold's lane is also offered as a **gate** (`Router.gates["mod"]`), so a route's `when` can wait on it. A modifier whose input is not live this frame (a scheme never fed, a name the rig lacks, an input not chosen, a hand out of view) is **dormant: its lane reads NaN**, so a route on it lets go exactly as a route on that source would; its memory starts afresh when the input comes back. Its published rest stays 0. So on return from dormancy a `threshold` whose input comes back already above `on` fires at once (a hand re-entering the box hot is a rising edge), and a `smooth` takes its first reading as it is, with no glide in. Both are as built. A non-finite output (an input reading ±inf) counts as dormant for that frame and drops the memory too.
**Other options:** a dormant lane at its rest 0 (the prompt's wording) — then a `position` route on it would pin the target at 0 instead of handing the base back; a names map (`mod:smooth1`).
**To reverse:** one line in `Router._step_modifier`.
**Rough edge:** a combine with one dormant input is wholly dormant (no "use what's there").
**Judge it:** Y.3.

**2xx — Ids and what a removal leaves.**
**Built:** `next_id` is one past the highest id held (`mod.1`, `mod.2`…), so a removed modifier's number is not reused while a higher one stands. Removing a modifier drops its params; a route on its lane stays, dormant (a load drops it with a note instead).
**Other options:** the lowest free number; removing the routes on its lane with it.
**To reverse:** `modifiers.next_id` / `Bindings.remove_modifier`.
**Rough edge:** removing the highest and adding again reuses its number, and a dormant route left on that lane wakes on the new node.
**Judge it:** Y.4.

**2xx — Where a modifier's params live in the preset.**
**Built:** in its entry only (`{"id", "kind", "in", <params>}`; an enum by name, a toggle as a bool), at their **bases** (a performer riding one never reaches the file). `values` leaves out every `mod.*` id, so a preset saved here loads on the base build with only the new key ignored; a `mod.*` id hand-written into `values` is ignored with a note. The `modifiers` key is written only when there is one (an older preset saves byte-for-byte as before). `mod` is a performance group with no module presets (`preset.NO_MODULE`, beside `macro`; the PRESETS overview leaves it out).
**Other options:** the params in `values` too.
**To reverse:** `Presets._values`.
**Rough edge:** none known.
**Judge it:** Y.5.

**2xx — A desk template's modifiers in a save.**
**Built:** a preset that names a template lands the template's modifiers with its own overriding by id (the merged set held, and drawn, in id order: `set_modifiers` sorts by id), and a save writes only the entries that differ from the template's **as the load read them** (the desk's `compact_desk` rule), so a fix to the template reaches every preset that uses it at the next load.
**Other options:** a save writing the whole list (then a template fix never reaches a preset saved once).
**To reverse:** `Presets._modifiers_part`.
**Rough edge:** a template's modifier the preset removed comes back at the next load: there is no "none" entry (the desk has dark rows; modifiers do not yet).
**Judge it:** Y.6.

**2xx — Undo over the modifiers.**
**Built:** the modifiers and their params are watched as one table part (`undo.TABLE_GROUPS = ("mod",)`: their params are not watched as bases), so adding, removing, re-wiring and a param's drag are each a step, and a restore puts the node and its params back together (`Bindings.set_modifiers`). The strip's +, × and input combos push named steps ("add modifier smooth", "delete modifier mod.2", "modifier input mod.2"); an input pick replaces the modifier whole.
**Other options:** the params watched as bases (then adding a modifier — a new id — would be no step).
**To reverse:** `undo.TABLE_GROUPS`.
**Rough edge:** a restore re-declares every `mod.*` param (a performer riding one picks it up again next frame).
**Judge it:** Y.7.

**2xx — Learn and a `mod:` source.**
**Built:** `Learn.accepts` takes a `mod:` lane only for a learn armed for anything (want None) or for "mod"; never a desk, pad, hand or role learn. `learn_source("mod:1")` lands a push / position route like a hand axis. No "Learn mod" menu entry was added (nothing physical moves a modifier).
**Other options:** a "Learn modifier" entry that waits for a modifier's output to move.
**To reverse:** two lines in `Learn.accepts`.
**Judge it:** headless only (`test_learn_takes_a_mod_lane_as_a_continuous_source`).

**2xx — The MODIFIERS strip's layout.**
**Built:** between the routes and the desk on ROUTING: a title with a kind combo and "+ modifier" flush right; then per modifier one line — "MOD n", its kind, an input combo per input (the route sources plus the other modifiers' lanes, never its own), the live output bar and number ("dormant" while not live), × — and a second line of its params as the panel's own widgets (slider, checkbox, combo), so Learn, "Route a lane here…" and the base → effective readout come with them. The kind is fixed once added. The page filter matches a modifier by id, "mod n", kind and inputs.
**Other options:** a kind combo per modifier (change in place); the strip under the macros.
**To reverse:** `ui_routing.modifiers`.
**Rough edge:** three params on a narrow panel make short sliders; no live bar of the inputs.
**Judge it:** Y.8.

## 2. Hand-check drafts (plan 28)

**Y.1 — Each modifier kind does what its name says.**
`Headless:` `tests/test_modifiers.py::test_curve_is_linear_at_zero_bends_both_ways_and_inverts`, `…scale…`, `…smooth…`, `…combine_mul_and_cross`, `…threshold…`, `…delay…`.
Setup: ROUTING, a preset with a route from band 0. Add one modifier of each kind on `lane:0` (the kick); route `mod:<n>` onto `view.bright` (position, depth 1) one at a time.
*Pass:* curve bends the brightness's response as shape moves; scale doubles it with × 2; smooth's release makes the brightness fall slowly after each kick; threshold flashes once per kick for the hold; delay looks the same as the raw route.
*Fail:* a modifier's output bar does not move with the music (an input not live — check the input combo); a threshold flashing continuously (on/off too close to the band's floor).

**Y.2 — A smooth on a spring rings.**
`Headless:` `test_smooth_with_spring_on_overshoots_and_settles`.
Setup: a smooth on the right hand's height, spring on, attack 0.2; route it onto `camera.zoom`.
*Pass:* a quick raise of the hand overshoots and settles; a smaller attack is snappier.
*Fail:* no overshoot (spring toggle not reaching the param).

**Y.3 — A modifier whose input goes away lets its routes go.**
`Headless:` `test_a_modifier_publishes_a_lane_a_route_can_source`, `test_a_modifier_whose_input_the_rig_lacks_is_dormant`.
Setup: a smooth on `hand:right.energy`, routed (position) onto `fx.acid.mix`. Take the right hand out of the box.
*Pass:* the strip says "dormant"; the acid mix returns to its setting at once.
*Fail:* the mix sticks at the last value or drops to 0.

**Y.4 — A removed modifier's route goes dormant.**
`Headless:` `test_the_mod_group_is_performance_and_its_params_come_and_go`, the ROUTING test's last lines.
Setup: two modifiers, a route on `mod:2`. × the second.
*Pass:* the route stays listed and does nothing; ⌘Z brings the modifier back and the route works again.
*Fail:* the route is removed, or the target sticks.

**Y.5 — A preset holds its modifiers; bindings.json never does.**
`Headless:` `test_modifiers_live_in_the_preset_and_never_in_bindings_json`, `test_an_older_preset_without_the_key_loads_as_before`.
Setup: build two modifiers on ROUTING; save the preset as a new name; load another preset, then this one; open `<home>/bindings.json` and the preset file.
*Pass:* the modifiers come back with their values; the preset file has a `modifiers` list after `routes`, no `mod.*` id in `values`; `bindings.json` names no `mod`. A factory preset loads with no note and shows no modifier.
*Fail:* a `mod.` line in bindings.json; a dirty dot on a factory preset just loaded.

**Y.6 — A template's modifier reaches every preset that uses it.**
`Headless:` `test_a_template_may_carry_modifiers_and_a_preset_overrides_by_id`.
Setup: a desk template file in `<home>/desk/` with a `modifiers` list (a smooth on the right hand's energy); two presets naming it, one with its own `mod.1` of a longer release.
*Pass:* both presets show the template's modifiers; the one with its own `mod.1` shows its release; editing the template file and reloading changes the other preset's modifier.
*Fail:* a save writes the template's modifiers into the preset (then a template edit no longer reaches it).

**Y.7 — Modifier edits are undo steps.**
`Headless:` `test_adding_and_editing_a_modifier_are_undo_steps`.
Setup: add a modifier, drag its release, pick another input. ⌘Z three times, ⇧⌘Z three times.
*Pass:* each ⌘Z takes back one change, the last one removes the modifier; redo puts them back.
*Fail:* the add is not undoable, or one ⌘Z takes two changes.

**Y.8 — "Right hand energy, smoothed, times band 0, into acid mix" from ROUTING alone.**
`Headless:` `test_the_routing_page_builds_the_smoothed_energy_times_band_patch`, `test_the_modifiers_strip_draws_between_the_routes_and_the_desk`.
Setup: the hands on, music playing, a preset with ACID on. On ROUTING: + modifier (smooth), input `hand R energy`, release 0.6; + modifier (combine), inputs `mod 1 smooth` and `0 sub`, how mul; + route, source `mod 2 combine`, target `fx.acid.mix`, op pos, depth 1.
*Pass:* the acid comes in as the right hand moves fast and pulses with the kick; it fades out over ~0.6 s when the hand stops; the strip's bars show both outputs live.
*Fail:* the combine reads 0 (an input combo not set); the acid does not move (the route's source combo not offering `mod 2`: one frame after adding it, it should).

## 3. As-built notes

### What was built (N1)
- `hyperspace/modifiers.py`, a leaf (imports `motion`, `tapers` only; in `hotreload.MODULES` right after `motion`, before `routing`): `Modifier(id, kind, inputs, params)` with `to_json` / `from_json`, `KINDS`, `PARAMS` (each kind's `Spec`s), `INPUTS`, `OUT` (threshold → trigger), `ModState`, `step(m, inputs, state, dt)`, `next_id`, `number`, `id_of`, `param_id`.
- `routing.py`: `declare_modifiers(reg, mods)` (the `fx.declare` pattern: every `mod.*` dropped, then `mod.<n>.<p>` per modifier); `Bindings.modifiers` (a tuple, class default `()`), `modifiers_serial`, `modifier`, `modifiers_doc(reg)`, `set_modifiers(doc, reg)`, `add_modifier`, `remove_modifier` — `to_json` and `is_session_row` untouched; `Router._reading`, `_step_modifier(mid, dt, lanes)` (**the N0 seam: one call per modifier node**), `_publish_modifiers`, `lane_kinds`, `_step_modifiers(analyzer, dt)` — one call at the top of `Router.modulate`, stepping every modifier in id order and feeding `mod`.
- `params.py`: `"mod"` appended to `PERFORMANCE_GROUPS`.
- `preset.py`: `MODIFIERS_KEY`, `NO_MODULE`, `merge_modifiers`; `load_doc` reads the template's and the preset's modifiers before the routes, drops a route onto a missing `mod:<n>` with a note, lands the modifiers and their params with the values (and puts them back if the load is refused); `document` writes `modifiers` after `routes` (compacted against a template), `values` without `mod.*`; `signature` includes the modifiers; `dumps` writes one entry a line.
- `undo.py`: `TABLE_GROUPS`, the modifiers as a fingerprint part, a `State.modifiers` field, restored through `set_modifiers`.
- `learn.py`: `accepts` takes `mod:` as a continuous source.
- `ui_routing.py`: the MODIFIERS strip (`modifiers(panel, router)`) between the routes and the desk, and its plain functions `modifier_sources`, `add_modifier`, `set_modifier_input`, `remove_modifier`, `modifier_output`, `mod_hay`; `_sources` skips a lane published with an empty label; `found` counts modifiers.
- `ui_presets.py`: the overview leaves `mod` out.
- Fixtures (force-added): `tests/fixtures/modifiers/presets/mod-energy.json`, `mod-missing.json`, `mod-templated.json`, `tests/fixtures/modifiers/desk/mod-rig.json`.

### What no person has verified
- The strip drawn at the machine (layout, widths, the bars), every kind on live music and real hands, a template carrying modifiers in the owner's library.

### Known rough edges
- Until N0, modifiers step in id order: a modifier reading a higher id reads last frame's output, and a modifier's own params (`mod.<n>.<p>`) moved by a route land one frame late (the existing lag rule).
- A template's modifier cannot be removed by a preset (no "none" entry).
- A combine `add` is unclamped.
- A removed highest id is reused by the next add.

## 4. Where the documents and the code differ
- The prompt says a dormant modifier's lane "stays at its rest, 0"; the code publishes NaN (not live) with the rest 0, so routes on it let go the way they do on any absent source (row "address form" above). The design's intent ("kept dormant, as a dormant route is today") is what NaN gives.
- `curve`'s table option is left out as the prompt says; the design's "S-curve" shape is also not built (exponent only).
- "`Router.feed` of `mod`": the lane is written through `Router.feeds["mod"]` (published with `feed` when the modifiers change, then written in place per node), so a per-node write needs no copy.
- No `docs/` file was edited.
