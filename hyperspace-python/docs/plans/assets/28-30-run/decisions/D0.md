# D0 — decisions, hand checks, as-built notes

Branch `plan-30-d0-effect-nodes`, base `5d18192`. Rows numbered `2xx` and
checks `X.n` for the docs WP to number.

## 1. Register-row drafts

### 2xx. The pipeline end keeps the class name `Fx`, its node names and its SYSTEM lines

- **Built.** `graph.Fx` is now the thin pipeline end: its `image` input is
  the last effect of its pipeline's run, its `paint` paints that input,
  and `run` keeps every job it had (direct-to-output, the frame texture,
  `bent` / `fallback` through `Fx.source` / `Fx.layer`, the error path
  marking the views). The nodes are still `fx`, `fx(scene+hands)`,
  `fx(hands)` and the SYSTEM page keeps their lines. Its line now reads
  the end's own work beyond its effects' passes, which is none (0.00):
  the time moved to the effects' own lines.
- **Other options.** A new class (`End`, `Pipeline`), with `Fx` gone or
  an alias: every test, tool and document that names `fx` / `Fx` changes,
  and the golden manifest's recorded `nodes` list (`frames.json` fixtures'
  `said.nodes`) would move.
- **To reverse.** Rename the class and `FX_NAMES`; re-record the
  manifest's `nodes` lists (no pixel moves).
- **Rough edge.** The end node's own `fx` line always reads 0.00: the
  end's paint is not charged there (it runs no pass of its own, and on
  this Mac's tile GPU the passes' work lands in the effects' lines or in
  none). 0.00 on `fx` does **not** mean the effects cost nothing: their
  cost is on their own lines (`acid`, `huecycle` …) just above it.
- **Judge it.** Check X.1.

### 2xx. An off effect is read through by its consumer: no pass, no texture, no node change

- **Built.** `graph.Effect.paint` of an effect that is not in the frame
  chain's `FxState.chain(FRAME)` this frame (switched off, mix 0, the
  stack bypassed, aimed at the faces) or whose file never compiled paints
  its input straight into its consumer's framebuffer; `image` returns the
  input's. Every effect instance is in every run on or off, so a chip
  switched on or off rebuilds nothing (`Renderer._graph_for` rebuilds
  only when `FxState.names()` — the list in order — changes: an order, an
  instance, a file). An effect aimed at the faces stays in the frame run
  as an off node, so retargeting rebuilds nothing either.
- **Other options.** Rewire the edge around an off node each frame (the
  graph's shape follows the chips; a rebuild or a per-frame rewire); a
  run holding only the on effects (a rebuild on every chip toggle).
- **To reverse.** `Effect.paint` / `image` and `_graph_for`'s key.
- **Rough edge.** Thirteen effect nodes per pipeline whatever is on (up
  to 39 with all three pipelines); invisible except in `repr(graph)`.
  A file that fails to compile now reads through instead of the old
  block's copy through a half-float texture (the old "everything on
  failed to build: a copy" path) — the picture is the same within
  half-float rounding; `run_one` still copies if ever asked.
- **Judge it.** Check X.2.

### 2xx. The effects' pool is the frame chain's half-float textures, two plus one per effect held, sized by the graph

- **Built.** `FxChain.pool(size, n)` hands out the chain's `f2` textures
  (the same format, filter and wrap `begin` made), at least `n`; `begin`
  (the faces' chain) is now `pool(size, 2)[0]`. `Graph.pool` is 0 with no
  effect node, else 2 plus one per effect read by more than one node.
  An effect writing `dst` paints its input into a pool texture that is
  not `dst` and not held, so a straight run alternates the two however
  long it is (the effect before writes from `dst`'s twin). An effect read
  by two consumers (D1's placements) paints once into a held texture and
  shows it 1:1 into each (`Effect.image`). A new graph that needs fewer
  textures releases the pool (`FxChain.fit_pool`); a size change makes
  all of them again; the pool grows by one if none is free.
- **Other options.** A pool owned by the graph (released with the graph
  object: the renderer's release paths and the hot-reload hooks would
  need it too); per-effect textures (13 × 3 half-float frames).
- **To reverse.** Local to `FxChain.pool`, `graph._spare`, `Graph.pool`.
- **Rough edge.** A held texture is shown through `Renderer._show` 1:1
  into each consumer: one copy more than a direct pass, and the second
  consumer's picture is the half-float one (pixel-exact for D0's graph,
  which never holds one; D1's placements will). **The aliasing
  constraint D1 inherits:** a held effect's texture must never be the
  framebuffer its consumer paints into (an on effect upstream of a
  held one paints the held effect into a pool texture; showing the held
  texture into that same texture is a GL feedback loop). Built so:
  `Effect.paint`'s held branch makes the picture with
  `Effect._make(frame, avoid=dst)`, which picks the held texture with
  `_spare(frame, dst, hold=True)` — never `dst`, never one already held
  — and a held texture is never handed out again that frame, so no later
  consumer's `dst` can be it. The pool stays 2 + one per held effect.
  Test: `test_a_held_effect_read_through_the_pool_is_never_its_consumers_target`
  (review round 1).
- **Judge it.** Check X.3 (D1's fixtures exercise the held path).

### 2xx. An effect's node is named by the effect in the scene's pipeline and with the pipeline's suffix in the others

- **Built.** `graph.effect_node_name`: `acid`, `acid.2`, `palette` in the
  scene's pipeline (SYSTEM's line, the word D1's placements name),
  `acid(scene+hands)` / `acid(hands)` in the others — the pattern of
  `fx(scene+hands)`. An effect whose file name another node has (a
  `scene.glsl`, `capture.glsl`, `output.2`) gets the params' prefix:
  `fx.scene`.
- **Other options.** `fx.<name>` for every effect node (unambiguous, but
  not the word the design and D1 use); one node shared by the pipelines
  (one effect node feeding three ends: the passes differ per pipeline).
- **To reverse.** `effect_node_name` and the collision rule in
  `default_graph`.
- **Rough edge.** With the hands through, SYSTEM shows both `acid` and
  `acid(scene+hands)` when both pipelines run (two outputs): correct, but
  two lines for one chip.
- **Judge it.** Check X.1.

### 2xx. SYSTEM shows a line only for an effect that ran a pass that frame

- **Built.** `Effect.TIMED` is False, so `Graph.timed` (and the golden
  manifest's recorded `nodes`) are as before; `Graph.timed_in(frame)` adds
  the effects that ran (`frame.stats["effects"]`) in their places, and
  the renderer hands that to the timer. An effect switched off drops its
  line once its last timed frame is read back (`PassTimer.LAG`).
- **Other options.** A line for every effect node, 0.00 when off (13 to
  39 dead lines).
- **To reverse.** `Effect.TIMED = True` and `end_frame(graph.timed)`.
- **Rough edge.** On this Mac's GPU (tile-based) a timer query is charged
  when a render pass is flushed, so an effect's line can carry its input's
  work or read 0.00 (see the measurement in the report): the lines are
  indicative, not an exact split.
- **Judge it.** Check X.1.

## 3. As-built notes (for `30-shader-nodes.md`)

### What was built — D0

- `graph.Effect(name, *, image=None, node=None)`: kind `effect`, one
  `IMAGE` in, `IMAGE` out; `effect` the instance's name (`acid.2`), `name`
  the node's (`effect_node_name`). `on(frame)`: in the frame chain's
  `FxState.chain(FRAME)` this frame and compiled (asked once a frame).
  Off: `paint` paints the input into the consumer's framebuffer, `image`
  is the input's — no pass, no texture. On: `_pass` paints the input into
  a pool texture (`graph._spare`) and runs `FxChain.run_one` into `dst`
  under `frame.timed(name)`, appending the node's name to
  `frame.stats["effects"]`. More than one reader (`Graph.readers`):
  made once into a held pool texture (`image`), shown 1:1 into each.
  `run` does nothing.
- `graph.Fx` is the pipeline end: input = the last effect; `effects`,
  `source`, `layer`, `bent` walk back through the run; `paint` moves the
  clocks once (`FxState.advance_to`), paints its input, counts
  `chain_runs`; `run` unchanged. `Output.settle` reads the through
  composite's blend from `end.source`.
- `graph.Graph`: `readers(node)`, `pool` (0, or 2 + held effects),
  `effects` (the list the runs were built from), `timed_in(frame)`.
- `graph.default_graph(views, wiring, clouds, effects=())`: each
  pipeline's source → one `Effect` per instance in `effects` → `Fx`.
- `fx.FxChain`: `pool(size, n)`, `fit_pool(n)`, `ready(name)`,
  `run_one(name, src, dst, t)`, `_uniforms` / `_opaque` shared with
  `run`; `begin` = `pool(size, 2)[0]`; `run` unchanged for the faces.
- `render.Renderer._graph_for`: the key gains `FxState.names()`; a new
  graph fits the pool. `_draw_frame`: `stats["effects"]`, and the timer
  is handed `graph.timed_in(frame)`.
- `ui.Panel.gpu_lines`: unchanged code (it shows whatever the timer
  keyed), docstring says the per-effect lines.
- Tests: `tests/test_graph_effects.py` (11). Changed assertions (decision
  5 / mechanism): `test_graph.py::test_the_timer_lists_…` and
  `test_golden_frames.py::test_each_node_has_a_rolling_median_in_ms` gain
  the effect's own line; `test_render.py::test_one_clock_reaches_…`,
  `test_render.py::test_a_frame_effect_runs_over_a_face_effect` and
  `test_outputs.py::test_a_raising_pipeline_…` spy on / break
  `FxChain.run_one` (the frame chain no longer calls `run`).

### What no person has verified

- The per-effect SYSTEM lines on the real window at the rig's 1080p cap
  (only headless numbers, below and in the report).
- Hot reload of `fx.py` / `graph.py` mid-show with effects on (the code
  path is the existing re-class; no test drives a reload with a run).

### Known rough edges

- Review round 1: an effect file named `fx` collided with the ends'
  names (`fx(scene+hands)`); the collision rule now reserves every
  `FX_NAMES` value, so it becomes `fx.fx`, `fx.fx(scene+hands)` ….
- The SYSTEM per-effect split is indicative on Apple's tile GPU: passes
  flushed inside another query are charged there (party-acid headless:
  the old `fx` line ~0.23 ms; the new lines sum to ~0.09 ms; frame wall
  time unchanged within noise, ~1.7 ms both).
- 13 effect nodes per pipeline whatever is on; `repr(graph)` is long.
- `Effect.on` builds the effect's fragment source string to ask
  `FxChain.ready`, and `run_one` builds it again: twice a frame per on
  effect where the block did it once (a few KB of string concat). Left
  as is after review round 1: a per-frame cache inside `FxChain._program`
  would need a frame counter the tests' direct `run` / `poll` calls never
  tick (an edited file would then keep a stale program within a test), and
  the cost is microseconds.

## 4. What the documents say that the code does not do / deliberate departures

- The prompt says the end node's `paint` "becomes paint my input" and
  "the end node's own line kept for the paint": built so, but the paint
  has no GPU work of its own (timing it around its input would nest
  queries, which `PassTimer` forbids), so its line reads 0.00.
- The prompt says the run is in "`FxState.chain(FRAME)` order (every
  instance, on or off)": `chain()` lists only the on ones, so the run is
  `FxState.names()` (the same order, every instance, every target); the
  on-test per frame is `chain(FRAME)`.
- "Release with it" (the pool): the pool lives on `FxChain` (released by
  `release_targets` / `release` as the old ping-pong textures were) and
  is fitted to each new graph (`fit_pool`), rather than owned by the
  graph object.
- `FxChain.run`'s "everything on failed to build: a copy" is not
  reproduced by the run: a never-compiled effect reads through.
- `default_graph` with no `effects` builds ends that read their sources
  directly (the frame with no effect); before D0 such a graph still ran
  the whole chain inside `Fx`. Only the renderer builds graphs, and it
  always passes the list.
